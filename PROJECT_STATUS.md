# OrcaFlow Project Status

**Audit date:** 2026-11-19  
**Scope:** Tracked project files and current working-tree source. This audit documents the existing MVP; it does not add or change application features.

## Executive summary

The repository is a small FastAPI backend scaffold, not yet a complete end-to-end MVP. Its manager endpoint classifies a submitted task, selects an agent name, and returns a proposed plan. The LangGraph workflow and API tests pass, but the selected agents do not exist as executable implementations, and there is no persistence or product frontend. Local-only Compose scaffolding is present, but not verified with Docker.

**Release assessment:** the supplied Compose configuration publishes only on localhost. Keep it local; do not expose it to untrusted networks without authentication and request controls.

## Review by requested area

### 1. Backend routes

- The OpenAPI schema exposes one application route: `POST /manager/tasks`.
- The request model requires a non-blank `task`; invalid blank input returns HTTP 422.
- The response contains `task_type`, `selected_agent`, and `execution_plan`.
- No database, identity, authorization, rate-limit, or request-size dependency is applied to the route.
- Default FastAPI documentation endpoints are enabled.

Relevant files: [routes.py](backend/api/routes.py), [dependencies.py](backend/api/dependencies.py), [main.py](backend/main.py).

### 2. Agent architecture

- `ManagerOrca` uses LangGraph for classification and routing.
- Classification is deterministic keyword matching, with unmatched tasks defaulting to analysis.
- Routing returns a selected agent name and a static plan; there are no concrete Research, Developer, or Analyst agent classes and no agent execution call.
- CrewAI and ChromaDB are listed as dependencies but are not used by the current application code. There is no implemented memory adapter.

Relevant files: [manager_orca.py](backend/agents/manager_orca.py), [base_agent.py](backend/agents/base_agent.py), [requirements.txt](backend/requirements.txt).

### 3. Database models

- SQLite is represented by a connection factory.
- No ORM models, SQL schema, migration mechanism, repository, or persistence endpoint exists.
- The request route does not use the SQLite dependency.

Relevant files: [database.py](backend/database/database.py), [dependencies.py](backend/api/dependencies.py).

### 4. Authentication and security

- No authentication or authorization mechanism is present.
- No credentials or secrets were found in the tracked application configuration reviewed.
- The route accepts arbitrarily long task strings; there is no application-level request-size limit or rate limit.
- Public deployment is not safe to assume from the code. Restrict access at the network edge until an application-level access policy is in place.

### 5. Frontend pages

- A static placeholder page is provided for deployment checks; it is not a product UI and has no task workflow.

### 6. Docker setup

- `docker-compose.yml` builds the backend and static Nginx frontend. The frontend is published on localhost only by default and proxies `/manager/tasks` to the internal backend.
- Docker and Docker Compose were unavailable in the audit environment; image build, service startup, health checks, and proxy behavior remain unverified.

### 7. Environment variables

- `ORCAFLOW_APP_NAME` and `ORCAFLOW_DATABASE_PATH` are the only environment variables read by the application.
- There is no example environment file, settings validation, or documented environment setup.
- The default SQLite path is relative to the process working directory, which should be considered when configuring a persistent deployment volume.

Relevant file: [settings.py](backend/settings.py).

### 8. Tests

- `python -m pytest -q -p no:cacheprovider` completed successfully: **8 passed**.
- The run emitted a Starlette deprecation warning about using `httpx` with `starlette.testclient`.
- Current tests exercise classification/routing, classifier injection, API output shape, and blank-task validation.
- There are no tests for database lifecycle/persistence, authentication, input-size controls, or deployment/startup configuration.

Relevant file: [test_manager_orca.py](backend/tests/test_manager_orca.py).

## Completed features

- FastAPI application factory with injectable settings, database adapter, and manager.
- `POST /manager/tasks` with request validation and a typed response.
- LangGraph-based task classification and routing to the three requested agent names.
- Deterministic execution-plan generation.
- SQLite connection factory and dependency providers.
- Local-only Docker Compose configuration and a static frontend deployment placeholder.
- Focused manager/API tests; all 8 pass in the audited environment.

## Incomplete features

- Actual research, development, and analysis agents and task execution.
- Database schema/models, migrations, and persistence.
- Memory/vector-store integration and use of the declared CrewAI dependency.
- Authentication, authorization, and request throttling/size controls.
- Product frontend, CI, and verified container deployment.
- Reproducible dependency and test-environment configuration.

## Broken features

No failure was reproduced in the implemented manager/API behavior covered by the current tests. The larger agent-execution and persistence flows are absent rather than implemented-and-broken.

## Audit notes

- The original audited tree contained 25 tracked files, including tracked Python bytecode. This follow-up adds only local deployment scaffolding and a static frontend placeholder.
- The working tree already had modifications in manager/test source and generated bytecode when audited. Those changes were left untouched; review conclusions are based on the current source.

## MVP stability priorities

1. Decide whether this MVP is private/local or network-accessible; enforce the corresponding access policy before public exposure.
2. Set clear MVP expectations: current agent routing produces plans only. Implementing actual agents is required before claiming task execution.
3. If persistence is in scope, add and test a schema/repository lifecycle before relying on SQLite.
4. Establish a reproducible installation/test/deployment path and add tests for any security and persistence controls before release.
